## 採用する仕組みと適用条件

`sql/page-cache-snapshot.sql` は PostgreSQL の MVCC snapshot を版番号にします。業務テーブルへの追跡トリガーや共通の書込ロックを追加しません。無関係なテーブルの更新も失効要因になります。

各要求で DB の版を確認し、一致する結果だけを再利用します。新規取得の前後で版が変われば再取得し、複数クエリの版が混ざる場合は画面全体を再試行します。版確認不可なら毎回通常取得し、失敗時に古い成功結果へ戻りません。メモリー上限は 64 件・8 MiB です。認証要求は共有キャッシュを使いません。

既存 RPC を監査し SQL を適用してから、`PAGE_CACHE_ENABLED=true` で有効化します。既定では無効で、データは毎回取得し、未導入の版確認 RPC への余計な通信も行いません。機能の有効・無効を切り替えても、古い結果を返す猶予時間は設けていません。

開いた画面は SSE の版通知で再取得し、手動・画面復帰・表示中 60 秒ごとの更新も維持します。通知機能が利用不可になった場合は、表示中に 60 秒間隔で再接続を試みます。通知を受けてからの再取得でも版検証を省略しません。

通知用の DB 確認は、同一プロセス内の同じプロジェクト・匿名 Cookie 境界で共有します。同じ境界のタブを増やしても監視用の確認は約 1 秒に 1 回です。最後の接続終了で停止します。上限は 32 境界、境界ごと 128 接続、全体 512 接続です。上限時は通常の定期取得へ戻ります。複数サーバープロセス間では共有しません。

既存 RPC の本文と呼出先を管理接続で確認することが有効化の前提です。STABLE 属性だけでキャッシュ可能とは判断しません。時刻・JWT・session 設定・外部データ等による結果差がないか、またはキーで区別できるか確認します。metadata とデータは同じ primary DB・統一した接続設定を使います。VOLATILE RPC、条件付き RLS、権限不足等では版を返さず通常取得へ戻ります。既存関数を無条件に STABLE へ変更しません。

ホームのログ RPC は集計・空欄補完を含む可能性があり、取得窓を勝手に広げて再利用していません。SQL 本文を確認するまで開始・終了時刻が完全一致する要求だけが再利用対象です。

適用準備は `node database-admin.mjs inspect`、本文確認後に `node database-admin.mjs apply-page-cache`、接続設定を確認して `PAGE_CACHE_ENABLED=true` を設定しサーバーを再起動する順です。構造の取得結果は Git 管理外に保存し、認証値・接続先・実レコードをレポートへ出しません。SQL 未適用のため、この追加キャッシュによる実 DB の速度向上は未検証です。

## 確認済みの範囲

隔離 PostgreSQL の 31 件で、INSERT・UPDATE・DELETE・TRUNCATE、ロールバック、commit 順序の逆転、未知の依存表更新、権限・RLS・VOLATILE 変更を確認しました。実 standby は起動せず、standby 拒否はコード確認のみです。

ローカル疑似 REST と Chrome による 21 件では、更新・削除の反映、競合の再取得、認証境界、失敗時の旧値不使用、SSE 通知、共有監視、上限、復旧時の自動再接続、終了後の監視停止を確認しました。通知の追随時間は `performance-cache-validation-2026-11-09.json` に保存しています。この値はページ速度でも実 DB の測定値でもありません。

多数接続の終了時、Request の signal だけでは監視が残る事象を検出したため、HTTP response の close から直接終了を伝えるよう改修しました。32 接続の全切断、同じ境界の片方だけの切断、ブラウザー終了を検証しています。Chrome 終了通知には 2 秒の猶予を置き、その後 1.3 秒間の DB 確認停止を検査します。

既存画面のブラウザー回帰 19 件、本体の単体テスト 35 件、静的配信 7 件、型検査と本番ビルドが通過しています。未採用のログ取得窓の検討用 6 件は本体の件数に含めていません。実環境への配備は未実施です。
