# 実 DB の改善・適用結果

Session pooler 経由の管理接続に成功し、実 DB へエラー集計用索引を追加しました。採用した設定は `PAGE_CACHE_ENABLED=false` で、画面データは毎回 DB から取得します。結果キャッシュによる古いデータの再利用はありません。

## DB 内部と API の結果

単位は ms。DB 内部の実行計画は前後各 1 回、API は変更前 5 回・変更後 10 回です。変更後は独立した 2 測定を全件合算し、遅いサンプルも残しています。

| 指標 | 変更前 | 変更後 |
| --- | ---: | ---: |
| エラー集計 SQL 実行時間 | 64.857 | 6.327 |
| 同 SQL の planning 時間 | 1.531 | 6.015 |
| 同 SQL の共有バッファ参照数 | 8877 | 46 |
| エラー API 中央値 | 171.523 | 53.282 |
| エラー API 最大 | 3139.942 | 127.274 |
| エラー API の失敗件数 | 1 / 5 | 0 / 10 |

変更前は正常ログを含む約 30.6 万行を調べ、大半を除外していました。新しい索引では当月 47 行・前月 195 行を直接絞り込みます。新索引は valid / ready を確認済みで、サイズは 16 KiB です。

API の変更前最大値には、既存 API が HTTP 200 とエラー本文を返したタイムアウト 1 件を含みます。成功時だけを選んだ比較ではありません。DB の実行時間と通信込みの API 時間も分けています。

## ページ遷移と直接読込

ローカル本番ビルド＋実 DB、Chrome 156.0.8078.80、1440×1000、CPU・ネットワーク制限なし。変更前 5 回、採用構成の変更後 10 回です。表内は「中央値 / 最大」、単位は ms です。

| 画面 | 遷移・変更前 | 遷移・変更後 | 直接読込・変更前 | 直接読込・変更後 |
| --- | ---: | ---: | ---: | ---: |
| ホーム | 130.4 / 179.1 | 125.7 / 160.2 | 755.0 / 1647.9 | 644.3 / 1849.4 |
| インシデント | 147.6 / 164.5 | 97.2 / 118.6 | 447.7 / 651.9 | 306.8 / 450.4 |
| エラー | 162.5 / 183.6 | 98.1 / 138.1 | 556.3 / 1640.8 | 341.8 / 646.6 |

ページ遷移は全画面で観測最大 200 ms 未満です。インシデント・エラー・ログインの中央値は 100 ms 未満になりました。初回読込を含む目標は未達で、ホームの直接読込最大は悪化しています。改善していない指標を除外していません。

直接読込は load、データ表示、更新完了と 2 フレームを待ちます。各試行のホームは新規ブラウザー context、続く画面は共通 assets を再利用します。直接遷移は全画面を一度訪問してからホバーなしでクリックし、遷移完了と 2 フレームまでを測ります。API を先に測るため、画面は DB 完全コールドの条件ではありません。

変更後の targets API は中央値 70.784 / 最大 862.505 ms、incidents API は 50.785 / 80.058 ms でした。SQL を変更していない API の差を索引の効果とは断定しません。ネットワーク・OS・DB 負荷は固定しておらず、本番配備後の画面速度の保証値でもありません。最終測定は 2026-11-09 08:34 JST に開始しています。

## キャッシュの採否

DB の版を毎回確認するキャッシュも、実際の匿名 API で稼働を確認し、各 5 回測りました。版確認だけの連続読取では版は変化せず、自己失効も起きませんでした。

| 画面 | 索引改善・キャッシュなしの遷移最大 | 鮮度確認付きキャッシュありの遷移最大 |
| --- | ---: | ---: |
| ホーム | 160.2 | 202.2 |
| インシデント | 118.6 | 282.9 |
| エラー | 138.1 | 121.1 |
| ログイン | 80.1 | 126.0 |

索引で集計が軽くなり、版確認の通信を加える利点が小さくなりました。全画面の遷移最大値を優先し、キャッシュなしを採用しています。キャッシュありの測定結果も同名 JSON に保存しています。採用後の再測定 5 回を加えた数値が上の変更後 10 回です。

## 適用内容と確認

- `sql/error-logs-optimized.sql`：既存エラー条件と同一の部分索引を CONCURRENTLY で追加。既存索引・業務データ・抽出条件を維持。
- `sql/page-cache-audited-rpcs.sql`：監査した本文 hash と一致する 2 RPC だけを STABLE・UTC・ISO に変更。本文・既存権限を維持。同一 REPEATABLE READ transaction で当月・前月・空の月と 1 時間・1 日・28 日の出力を比較し、不一致なら全変更を中止。
- `sql/page-cache-snapshot.sql`：将来キャッシュを有効にするための版確認関数を追加。MVCC、DB 再起動、JST 月、出力設定を版に含め、権限・RLS・VOLATILE 等が条件を満たさなければ通常取得へ戻す。現在の採用設定では呼び出さない。

隔離 PostgreSQL の索引・互換性・監査 migration 33 件、snapshot の鮮度検証 36 件が通過しました。実 DB でも 6 条件の出力一致、新索引の有効性・実際の利用、匿名版確認 API の稼働を確認しました。サブエージェントによる SQL 監査で、現在の定義に適用を妨げる指摘はありませんでした。

原本の関数定義とロールバック SQL は Git 管理外に保存しています。認証値・接続先・実レコードはこのレポートに含めていません。将来キャッシュを有効にする場合は、RPC 本文・呼出先・RLS の変更時に再監査し、データ取得と版確認を同じ primary DB・統一した設定へ接続する条件を維持します。

全サンプル・各段階の比較・失敗数は `performance-database-2026-11-09.json` に保存しています。
